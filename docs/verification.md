# Проверка стенда и нагрузочные испытания

На одном компьютере с Windows и Python 3.14.10 работали отдельные процессы координатора, тестового HTTP-сервиса и рабочих узлов. Каждый узел использовал собственный каталог и индивидуальный ключ. Сквозная проверка взаимодействовала с процессами по HTTP через loopback. Все загружаемые файлы в этих испытаниях содержали детерминированные тестовые данные.

## Воспроизведение

Из корня проекта выполните:

```console
python -m unittest discover -s tests -v
python verify_lab.py
```

В объединённой сборке прошли 27 тестов Python и четыре теста показателей мониторинга (`node --test tests/monitor.test.cjs`). Проверка `tests/browser_smoke.cjs` через Playwright и Chromium прошла сценарий входа, создания задания, просмотра серверов и аудита, а также проверила отсутствие горизонтального переполнения при ширине экрана 390 пикселей. Для запуска этой дополнительной проверки нужен установленный Playwright и доступный Chromium. Путь к браузеру можно задать в `LAB_CHROMIUM`.

Сквозные сценарии можно запускать отдельно с аргументами `--case recovery`, `--case load` и `--case fleet`. Для них нужны свободные локальные порты, доступ к loopback и место для временной БД и файлов. Нагрузочный тест записывает более 48 МиБ. Каждый сценарий создаёт собственный временный каталог и случайные ключи, а при выходе завершает свои процессы. Любая ошибка проверки возвращает ненулевой код.

## Отказ и восстановление

1. На трёх зарегистрированных узлах создан диапазон 0–59 с блоками по 12 ID и четырьмя потоками на узел. Первую аренду получил `worker-1`. Скрипт принудительно завершил его процесс и разрешил выдачу блока другим узлам.
2. В контрольном запуске этот же блок получил `worker-3` через **4,02 с** после отключения. Аренда составляла 4 с, интервал отправки heartbeat — 0,5 с. Измерение заканчивается по времени события выдачи в журнале координатора.
3. Перед принудительным завершением координатора скрипт запомнил **48 подтверждённых записей** через API. После запуска нового процесса с прежней БД он сравнил каждое поле этих записей. Все совпали. Остановленный агент был запущен снова.
4. В результате получено ровно 60 уникальных ID. В 46 случаях файл загружен, 12 материалов отсутствовали, один был запрещён и один пропущен по политике скачивания. Для всех 46 файлов совпали SHA-256 на диске и в подтверждённом результате. Число физических файлов совпало с числом завершённых загрузок.
5. Источник возвращал `403`, `404`, `429`, `500` и разрывал загрузки. Проверено наличие события об ограничении частоты, получение ответа `206` и правильность итоговых файлов после обрыва с поддержкой Range и без неё.
6. Проверены ответ 401 без ключа, ответ 403 зрителю при создании задания, отказ оператору в SSH-операции и фиксация отказа в аудите администратора.
7. Для отдельного задания резерв диска был задан выше свободного места на всех узлах. За 1,25 с аренды не появлялись. Снижение резерва разрешило выдачу. Проверены мягкая пауза, изменение потоков и лимита, возобновление и немедленная остановка.

## Нагрузка

| Испытание | Условия | Наблюдавшийся результат |
|---|---|---|
| Параллельные HTTP-проверки | Три процесса по 48 потоков, три блока по 48 ID, задержка каждого ответа 4,5 с | Источник измерил пик **144 одновременных HTTP-запроса**. Все 144 ID получили ожидаемый статус 404 за **8,81 с**, в среднем **16,35 ID/с** с учётом получения блоков и сохранения результатов. |
| Одновременные задания на крупные файлы | Три блока по одному ID, по 16 МиБ на файл | Все **48 МиБ** загружены за **1,63 с** от создания задания до завершения. Для каждого файла повторно проверены размер и SHA-256 по фактическим байтам на диске. |
| Много рабочих узлов | 20 отдельных процессов по пять потоков, диапазон 0–1999, блоки по 25, задержка 200 мс | В финальном прогоне после изменения очереди записи SQLite за **9,31 с** подтверждены 2 000 уникальных ID, по 100 на каждый узел. За период задания по свежим heartbeat зафиксировано **0 транспортных тайм-аутов** управляющих запросов, в журнале задания — **0 истёкших аренд**. |

Пик HTTP-операций измеряет счётчик активных обработчиков тестового источника на всём протяжении ответа. Настройка пула потоков сама по себе такого измерения не даёт. Скорости относятся к этому компьютеру, журналу SQLite и заданным задержкам.

При повторном полном прогоне объединённой сборки 19 ноября 2026 года блок перешёл от worker-1 к worker-3 за **4,12 с**. После рестарта сохранились все **48** ранее подтверждённых строк. Пик на трёх узлах снова составил **144** одновременные HTTP-проверки. Три файла по 16 МиБ были загружены за **1,59 с**. Сценарий с 20 процессами подтвердил 2 000 ID за **9,34 с**, по 100 на узел, без транспортных тайм-аутов координатора и истёкших аренд.

## Границы испытаний

Локальные процессы проверяют разрыв связи с узлом и восстановление состояния после перезапуска. Развёртывание на разных физических серверах, реальное SSH-управление systemd, ротация производственных сертификатов и характеристики внешней сети требуют отдельного инфраструктурного стенда. Изменение порога свободного места проверяет механизм допуска узла. Физическое заполнение системного диска в этом прогоне не выполнялось. Полная потеря диска с SQLite выходит за пределы сценария перезапуска.

## HTTPS и временная недоступность записи в БД

Команда `python verify_tls.py` создаёт временный удостоверяющий центр и серверный сертификат для loopback. Для выпуска сертификатов нужен OpenSSL, путь к нему можно передать через `--openssl`. На Windows проверен исполняемый файл OpenSSL из Git for Windows. Ключи и процессы удаляются по завершении сценария.

В контрольном запуске HTTPS-клиент с пустым хранилищем доверенных корней отклонил сертификат сервера. Клиент с тестовым CA смог управлять заданием. Отдельный агент зарегистрировался через HTTPS, получил блоки и подтвердил **16 из 16 файлов** по защищённому соединению с координатором. Mock-источник передавал детерминированные байты через локальный HTTP. Выполнен поиск всех сгенерированных ключей доступа во взятых ответах API, событиях, аудите и консольных журналах трёх процессов. Совпадений не обнаружено.

После первого подтверждённого ID независимое соединение SQLite удерживало транзакцию `BEGIN IMMEDIATE` **2,25 с**. В течение этого интервала WAL допускал чтение подтверждённых результатов, запись из координатора была недоступна, а обращение к изменяющему API вернуло **HTTP 503**. После освобождения БД агент завершил тот же диапазон без перезапуска. Данные первоначально подтверждённого ID совпали полностью, все 16 ID присутствовали ровно по одному разу.
