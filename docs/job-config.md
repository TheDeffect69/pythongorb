# Конфигурация и запуск задания

Команда `python jobctl.py submit` создаёт и запускает задание. Для демостенда `python demo.py` сначала задайте в окружении `LAB_OPERATOR_TOKEN` со значением `operator` из файла состояния. Для именованной учётной записи используйте секрет этого оператора. Адрес координатора по умолчанию — `http://127.0.0.1:8090`. Для удалённого API укажите `--coordinator https://coordinator.lab:8443` и установите доверенный CA.

```console
python jobctl.py submit --from 10 --to 29
python jobctl.py submit --to 29 --create-only
```

В первом примере обрабатываются 20 ID. При одном `--to` отсчёт начинается с нуля, при одном `--from` диапазон открыт сверху. Без файла и обеих границ запускается открытый диапазон с нуля. `--create-only` оставляет задание в состоянии `created`. CLI выводит ID сразу после создания. Если запрос запуска завершился ошибкой, проверьте существующее задание по выведенному ID.

## Единый файл стенда

Пример JSON находится в [fixtures/job.example.json](../fixtures/job.example.json). Объект `job` задаёт параметры задания, массив `servers` — узлы. Имена узлов должны совпадать с зарегистрированными ID. Пустой или отсутствующий список разрешает координатору использовать любой зарегистрированный узел. Неизвестные и дублированные ключи отклоняются.

| Область | Поля |
|---|---|
| Задание | `name`, `range`, `threads`, `chunk_size`, `request_timeout_seconds`, `max_retries`, `min_free_space_gb`, `global_rate_limit_rps`, `check_rps`, `download_rps`, `max_seconds`, `max_items`, `stop_on_consecutive_missing` |
| Сервер | Обязательные `name` и абсолютный `storage_path`. Индивидуальные `threads`, `min_free_space_gb`, `worker_rps`, `check_rps`, `download_rps` |
| SSH сервера | `host`, `ssh_port` (по умолчанию 22), `ssh_user`, `ssh_auth` со значением `agent` или `key`, `ssh_key` — абсолютный путь к смонтированному ключу на координаторе. Для локального узла всю SSH-группу можно опустить |

В файле принимается `range` как объект с границами `from`, `to` либо строка диапазона из задания. Аргументы `--from` или `--to` заменяют диапазон целиком. Например, `--from 5` задаёт открытую верхнюю границу независимо от конца диапазона в файле.

## Развёртывание на трёх машинах

Подготовьте параметры TLS, индивидуальные токены агентов и учётные записи согласно [инструкции развёртывания](deployment.md). Подставьте реальные адреса и каталоги в копию примера `lab.json`. Путь к ключу ссылается на секрет на координаторе. Содержимое ключей, пароли и токены в этот JSON не включаются.

На машине координатора:

```console
python jobctl.py coordinator --config lab.json --host 0.0.0.0 --port 8443 --cert /etc/lab/server.crt --key /run/secrets/tls.key --db /var/lib/lab/state.sqlite
```

Этот режим передаёт координатору локальный SSH-инвентарь и соответствие идентификаторов разрешённым каталогам. Только администратор меняет эти сведения в файле на сервере. Перезапустите координатор после изменения инвентаря. Ключи хоста должны быть заранее проверены и установлены в `known_hosts`.

На каждой машине агента запустите соответствующий ID, передав его `LAB_WORKER_TOKEN` через окружение:

```console
python jobctl.py agent --config lab.json --id worker-01 --coordinator https://coordinator.lab:8443 --source http://mock:8091
```

Агент использует каталог хранения указанного узла. Путь должен существовать или быть доступен для создания системной учётной записи агента. Имя `mock` указывает на управляемый HTTP-сервис лаборатории. Разместите на машинах стандартные модули проекта вместе с `jobctl.py`. Опция `--capacity` задаёт объявляемую ёмкость узла. Для реального запуска подберите её под ресурсы машины.

Когда узлы зарегистрированы, выполните на машине оператора:

```console
python jobctl.py submit --config lab.json --coordinator https://coordinator.lab:8443 --from 0 --to 99
```

CLI передаёт в API разрешённые ID и индивидуальные рабочие параметры одним запросом создания задания. SSH-адреса, пути ключей и файловых хранилищ остаются в локальной конфигурации развёртывания. Параметры узла из файла относятся к этому заданию. Величины `check_rps` и `download_rps` ограничивают частоту проверок и загрузок дополнительно к общему лимиту. Пустой лимит конкретного типа означает, что действует общий бюджет. Параметры работы узла можно проверить в панели, разделе «Серверы», а индивидуальные параметры задания возвращаются в `worker_settings` его API-описания.
