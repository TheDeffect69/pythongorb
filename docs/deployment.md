# Установка и эксплуатация

## Один компьютер

Скопируйте каталог проекта, убедитесь, что `python --version` показывает 3.11 или новее, и запустите `python demo.py`. Оба HTTP-сервиса слушают loopback. Требуются два свободных TCP-порта и доступ на запись в каталог состояния. Установка зависимостей из сети не нужна. Для группы на одном стенде выдавайте участникам только тот ключ, который соответствует их роли.

## Несколько машин

Установите Python 3.11+ на координатор и каждый узел. Разместите код релиза в `/opt/video-lab`. На координаторе подготовьте постоянный каталог для SQLite. На каждом узле создайте отдельного непривилегированного пользователя и каталог для файлов. Тестовый HTTP-источник доступен агентам по имени `mock` в доверенной сети лаборатории или по loopback при совместном размещении. Все процессы одного прогона должны использовать один экземпляр источника для воспроизводимых сценариев отказов.

Для общего стенда укажите в `LAB_USERS_FILE` путь к защищённому файлу менеджера секретов. Формат — JSON-объект, где ключом служит логин, а значение имеет поля `role` и `token`. Задайте отдельный токен каждому человеку и хотя бы одну роль `administrator`. Доступны также роли `operator` и `viewer`. Журнал аудита сохранит логин конкретного пользователя. При перезапуске координатор перечитывает файл и обновляет назначения ролей. В SQLite сохраняются только логины и роли. Локальный профиль вместо именованных пользователей использует отдельные ключи ролей из `LAB_ADMIN_TOKEN`, `LAB_OPERATOR_TOKEN`, `LAB_VIEWER_TOKEN`.

Передайте координатору также `LAB_WORKER_TOKENS` — JSON-словарь из ID узла и его индивидуального случайного секрета. Каждый агент получает только свой `LAB_WORKER_TOKEN`. Используйте разные криптографически случайные значения длиной не менее 32 байтов.

Для соединений между машинами настройте сертификат координатора с DNS-именем узла и доверенный корневой сертификат на агентах. Параметры порта, SQLite и TLS перечисляет `python coordinator.py --help`. Ограничьте доступ к API адресами стенда. К mock-сервису должны подключаться только узлы лаборатории. Запускайте каждый агент отдельной службой:

```console
python agent.py --coordinator https://coordinator.lab:8443 --source http://mock:8091 --id worker-1 --threads 8 --storage /var/lib/lab-worker
```

Для systemd поставляется `deploy/lab-worker.service`. Заполните защищённый файл `/etc/video-lab/worker.env` переменными `COORDINATOR_URL`, `MOCK_URL`, `WORKER_ID`, `WORKER_THREADS`, `LAB_WORKER_TOKEN`. При необходимости задайте `SSL_CERT_FILE` с путём к доверенному CA. Пользователь и группа `labworker` должны существовать. Настройте выходящий трафик агента только к координатору и тестовому источнику.

Для установки через systemd администратор копирует обе службы из `deploy/` в каталог системных unit-файлов, выполняет `systemctl daemon-reload` и размещает `deploy/worker_release.py` в `/opt/video-lab/deploy/`. Только администратор релизов должен иметь право записи в `/opt/video-lab`. Подготовьте первую версию командой ниже. Вместо `SHA256_РЕЛИЗА` подставьте контрольную сумму утверждённого файла, полученную отдельно от поставки:

```console
python3 /opt/video-lab/deploy/worker_release.py stage ./agent.py v1 SHA256_РЕЛИЗА
systemctl start lab-worker-update.service
systemctl enable lab-worker.service
```

Подготовка проверяет контрольную сумму и синтаксис, помещает код в новый каталог версии и переключает ссылку `next`. Служба обновления атомарно выбирает подготовленную версию как `current`, перезапускает агент и проверяет статус systemd. При ошибке перезапуска она возвращает предыдущую версию, если та была установлена. Для следующего релиза задайте новое имя версии, выполните `stage` и нажмите «Обновить агент» в панели. После переключения проверьте heartbeat на координаторе. Доступ к установке кандидата и право активировать уже подготовленный релиз можно выдать разным пользователям.

## Управление узлом по SSH

Переменная координатора `LAB_SSH_INVENTORY` указывает на локальный JSON-файл. Его ключ — зарегистрированный ID работника, значение содержит `host`, `port`, `user` и опциональный абсолютный путь `identity_file` к ключу, смонтированному менеджером секретов. При отсутствии пути используется SSH-agent или системная конфигурация OpenSSH. Заранее установите и проверьте host key в known_hosts. Рабочий пользователь SSH должен обладать только правом управления заданной службой. Браузер не получает ключи. Команды управления выполняются по фиксированному списку. Локальный профиль не требует SSH-сервера.

## Обновление и ротация

Поставьте задания на мягкую паузу и дождитесь завершения текущих блоков. Сохраните резервную копию базы средствами SQLite Backup и копию рабочих каталогов согласно политике стенда. При файловом копировании БД остановите координатор и учитывайте WAL. Разверните согласованный релиз координатора и агентов. При старте координатор применяет недостающие миграции транзакционно. Проверьте регистрацию узлов, сохранённый прогресс и тестовое задание перед продолжением основной работы.

Для плановой ротации замените соответствующий секрет в источнике конфигурации координатора и агента и перезапустите затронутые процессы. Старый ключ должен получать HTTP 401. Обновляйте SSH-ключи через менеджер секретов и список разрешённых ключей узла. Не сохраняйте ключи в коммитах, отчёте или скриншотах.
