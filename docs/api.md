# API координатора

Сводка задания содержит `total_items` и `progress_percent`. Для конечного диапазона размер включает обе границы и учитывает ограничение `max_items`. Для открытого диапазона без лимита оба значения равны `null`. Прогноз `eta_seconds` использует среднюю скорость подтверждения ID за время с начала работы. Для открытого диапазона и для паузы прогноз не выдаётся. При завершении конечного задания ETA равна нулю.

Запуск повторно проверяет сохранённую конфигурацию. Событие `validating` предшествует `running`, при непригодной конфигурации появляется `failed` с причиной `invalid_saved_configuration`. Немедленная остановка проходит через `stopping` в `stopped`. Эти короткие переходы фиксируются в журнале в той же транзакции и видны после обновления страницы.

Базовый префикс — `/api`. Передавайте ключ роли или узла в заголовке `Authorization: Bearer <token>`. Для запросов с телом используйте `Content-Type: application/json`. Успешные ответы возвращают HTTP 200. Ошибки содержат JSON-поле `error`. Типовые коды — 400 при ошибке параметра, 401 при недействительном ключе, 403 при недостаточных правах, 404 для неизвестного ресурса, 409 при конфликте состояния или истёкшей аренде, 503 при временной недоступности хранилища.

## Задания и результаты

| Метод | Путь после /api | Действие |
|---|---|---|
| GET | /me | Роль текущего пользователя |
| GET, POST | /jobs | Список заданий или создание задания |
| GET, PATCH | /jobs/{id} | Сводка или изменение потоков, общего и раздельных лимитов запросов, резерва диска и списка узлов |
| POST | /jobs/{id}/start, /pause, /resume, /stop | Переход состояния. Каждый суффикс относится к одному заданию |
| POST | /jobs/{id}/retry | Явная повторная обработка ошибочных элементов |
| GET | /jobs/{id}/items | Подтверждённые элементы с метаданными, файлом и статусом |
| GET | /jobs/{id}/states | Последнее сохранённое состояние каждого ID из выданных блоков |
| GET | /jobs/{id}/items/{external_id}/history | Переходы ID по всем попыткам, от первого к последнему |
| GET | /jobs/{id}/events | События задания |
| GET | /events | События по всем заданиям |
| GET | /audit | Аудит действий, доступен администратору |

Пример тела при создании:

```json
{"name":"Демонстрация","range":"[0,59]","chunk_size":5,"threads":8,
 "rate_limit":20,"check_rps":16,"download_rps":8,"max_retries":4,"request_timeout_seconds":20,
 "min_free_space_gb":0,"worker_ids":["worker-1","worker-2","worker-3"]}
```

Список узлов можно опустить. Для диапазона допустимы `"[A,B]"`, `"A"`, `"[A,]"` и `""`, а также объект с необязательными полями `from` и `to`. Границы включительны. Для ограничений предусмотрены `max_items`, `max_seconds`, `stop_on_consecutive_missing`. Значение `null` отключает соответствующее условие. Сначала создаётся запись с ID и статусом `created`. Чтобы начать обработку, отправьте `POST /api/jobs/{id}/start` с пустым объектом.

Получение результатов поддерживает `status`, `external_id`, `worker_id`, `offset`, `limit` и `format=csv`. События фильтруются по заданию, узлу, ID материала, результату, операции и времени `from` и `to` в секундах Unix. Для пагинации по умолчанию возвращается 100 записей. Сводка задания содержит обработанные ID, находки, файлы, ошибки, объём данных, средние скорости и оценку оставшегося времени. Для открытого диапазона ETA равна `null`.

## Рабочие серверы

| Метод | Путь после /api | Кто вызывает и что получает |
|---|---|---|
| GET | /workers, /workers/{id} | Пользователь читает список или сводку узла |
| PATCH | /workers/{id} | Оператор меняет `enabled`, `threads`, `worker_rps`, `check_rps`, `download_rps` и `min_free_space_gb`. Значение `null` снимает индивидуальное переопределение |
| GET | /workers/{id}/metrics | Последние снимки, необязательный параметр `limit` |
| POST | /workers/{id}/service | Администратор передаёт `action` из списка `status`, `start`, `restart`, `update`. Нужен настроенный SSH-инвентарь |
| POST | /workers/register | Агент передаёт `id`, `name`, `version`, `storage_path`, `threads` |
| POST | /workers/{id}/heartbeat | Агент отправляет `metrics` и, при работе, `chunk_id` и `attempt`. Получает действие и настройки потоков |
| POST | /workers/{id}/lease | Агент запрашивает работу. Ответ содержит `chunk` либо `null` |
| POST | /workers/{id}/permit | Запрос разрешения на HTTP-операцию типа `check` или `download`. Ответ содержит `granted` и `wait` в секундах |
| POST | /workers/{id}/progress | Подтверждение результата одного ID |
| POST | /workers/{id}/lifecycle | Пакет промежуточных переходов одного ID в действующей аренде |
| POST | /workers/{id}/complete | Подтверждение блока после обработки всех его ID |
| POST | /workers/{id}/fail | Возврат незавершённого блока |

Каждый агент действует со своим ключом. В операции по активной аренде передавайте `chunk_id` и `attempt`, полученные при выдаче блока. В `progress` дополнительно передаются `external_id`, конечный `status`, при наличии — `metadata`, `file` и краткий код `error`. Для готового файла передаются `storage_path`, `size`, `sha256`. Текущие проверки и загрузки видны в heartbeat узла. При HTTP 429 или 5xx агент сообщает о результате координатору через `permit` с `result_status` и `retry_after` в секундах.

Веб-интерфейс и агент используют один контракт. Для изменения обязательных полей протокола выпустите совместимую версию координатора до обновления агентов. Отсутствующие необязательные поля следует обрабатывать как значения по умолчанию.

## Лимиты частоты и выдача работы

Все лимиты частоты задаются целыми числами от 1 до 10 000 запросов/с. У задания `rate_limit` ограничивает суммарное число запросов всех агентов, по умолчанию 20. Поля `check_rps` и `download_rps` отдельно ограничивают проверки страниц и запросы скачивания. По умолчанию оба равны `null`. Например, при значениях 20, 16 и 8 одновременно действуют все три ограничения.

У узла `worker_rps` ограничивает все запросы с этого узла, `check_rps` и `download_rps` относятся к соответствующему виду работы. Значение `null` снимает конкретный дополнительный лимит. Параметры `PATCH` вступают в силу со следующего запроса `permit`, включая запросы уже выданных блоков. Параметры запуска агента также могут ограничивать его локальную частоту.

Для создания задания с индивидуальными настройками передайте поле `worker_settings`. Ключи объекта должны входить в явный список `worker_ids`. Весь запрос сохраняется атомарно. Например, можно отправить:

```json
{"range":"[0,500]","worker_ids":["worker-1","worker-2"],
 "threads":8,"rate_limit":40,
 "worker_settings":{"worker-2":{"threads":12,"worker_rps":25,"download_rps":6,"min_free_space_gb":20}}}
```

Эти настройки действуют в пределах задания. Индивидуальные потоки в задании имеют приоритет над остальными настройками потоков. Индивидуальный резерв в задании заменяет общий резерв задания. Постоянный минимальный резерв узла продолжает действовать. При получении разрешения расходуется по одному токену каждого применимого лимита. Если хотя бы один лимит исчерпан, агент получает `granted=false` и время ожидания `wait`. Все агенты задания соблюдают `Retry-After` и общий сниженный лимит после ответов 429 или 5xx. Номинальная частота восстанавливается постепенно.

Среди подходящих заданий первым получает блок то, которому дольше всего не выдавалась работа. При отсутствии истории используется заданный `chunk_size`. Для нового блока координатор оценивает среднюю скорость обработки по свежим снимкам метрик узла и ориентируется на объём полусрока аренды. Доля недавних ошибок уменьшает объём выдачи. Если одновременно падает скорость обработки и растёт по сравнению с предыдущими интервалами сетевой или дисковый ввод-вывод, размер дополнительно уменьшается. Отсутствующие аппаратные счётчики пропускаются, после перезапуска отрицательные разницы счётчиков отбрасываются. Допущенный к работе узел получает хотя бы один ID. Границы возвращённого в очередь блока сохраняются.

## История обработки ID

Для чтения состояний достаточно роли `viewer`. Обе выборки поддерживают `limit` (1–5000) и `offset`. Список состояний дополнительно фильтруется по `external_id`, `worker_id` и `status`. Запись содержит `job_id`, `external_id`, `worker_id`, `chunk_id`, номер аренды `attempt`, порядковый номер перехода `seq`, статус и время фиксации координатором `ts` в секундах Unix. До первой выдачи блока идентификаторы ещё не материализованы, что позволяет обслуживать открытые диапазоны.

При выдаче блока координатор записывает `pending` для всех незавершённых ID. Агент прикладывает `external_id` и массив `transitions` к обычному сообщению `permit` или `progress`. Для отдельной отправки используется `lifecycle`. Пример одного перехода — `{"chunk_id":1,"attempt":2,"external_id":7,"transitions":[{"seq":1,"status":"checking"}]}`. Нумерация начинается с единицы заново для каждого ID и каждой новой аренды. Повторный отчёт безопасен. Нарушение порядка возвращает HTTP 400, устаревшая аренда — HTTP 409. При остановке, отзыве или истечении аренды незавершённые ID получают `cancelled`. После повторной выдачи начинается новая последовательность. Подтверждённый результат и его конечный переход сохраняются одной транзакцией.

Для запроса разрешения на скачивание необязательное поле `download_seq` задаёт номер перехода в `downloading`. Координатор фиксирует этот переход атомарно с выдачей разрешения. Пока запросы ограничены по частоте, ID остаётся в `download_queued`.

После обновления старой БД история содержит ранее подтверждённые результаты с `attempt=0`. Промежуточные события прошлой версии недоступны. Для активных аренд создаются начальные состояния незавершённых ID.
